# M2 Accounts Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans for the already authorized M2 milestone.
> Implement inline in the current checkout and branch, verify each responsibility, and commit it
> separately. Do not repeat design approval or create a worktree. Finish with one independent review.

**Goal:** Two real users can register, manage private accounts and devices, maintain contacts, and
recover access through optional verified email in the actual frontend.

**Architecture:** PostgreSQL owns identities, hashed opaque sessions, relationships, challenges, and
leased mail jobs. Rust modules own their business transactions; Axum exposes typed contracts and
Valkey guards sensitive requests. The Worker sends encrypted queued mail through Lettre. Connected
account routes never mount demo chat state; actual messaging remains M3.

**Tech stack:** Existing Rust/Axum/SQLx/Tokio/Utoipa and React toolchain, RustCrypto Argon2id,
SHA-256 and AES-GCM, cookie, redis client for Valkey, Lettre, and optional Mailpit capture.

**Spec:** [Approved product design](../specs/2026-11-08-complete-product-design.md), sections 4, 10,
12-16, and [M2 scope](./2026-11-08-product-milestones.md#m2-accounts-sessions-contacts-and-recovery).

## Global constraints

- Preserve current checkout and grouped Conventional Commits. All code/docs/comments use English.
- Follow the owner's readability rules: semantic paragraphs, documented public functions, no
  compressed code, 100 columns, at most three control-flow levels/chained calls, and multiline
  literals with at least three members. Prefer libraries for protocol and cryptographic work.
- Usernames are immutable, case-insensitive ASCII letters/digits/underscore, 3-32 characters;
  reserve system names. Display names, biographies, and optional phone text are separate.
- Passwords support Unicode and long phrases without truncation. Initial policy is 12 characters
  minimum and 1,024 UTF-8 bytes maximum. Argon2id defaults to 19 MiB, two passes, one lane, with
  bounded blocking work; parameters remain explicit server configuration.
- Sessions use random 256-bit opaque cookies, store hashes only, and check PostgreSQL on every
  authenticated request. Initial absolute expiry is 30 days, inactivity expiry seven days, recent
  authentication ten minutes; activity writes may be coalesced for five minutes.
- Cookies are HttpOnly and SameSite=Lax, Secure for HTTPS. Plain HTTP is allowed only for explicit
  loopback development origins. Unsafe requests require exact Origin and a custom request header;
  authenticated mutations additionally require a session-bound CSRF value returned by the API.
- Registration/login/recovery/discovery are bounded and rate-limited through Valkey. Limiter failure
  rejects sensitive admission; existing authenticated reads remain available. Never trust arbitrary
  forwarded IP headers: the Compose gateway must overwrite the dedicated client-address header.
- Email is optional/private and unique when verified. Replacement preserves the old verified email
  until confirmation. Challenges expire after 15 minutes and are single-use. Reset revokes every
  session; password change revokes other sessions and rotates the current token.
- Contacts are directional, capped at 1,000; incoming calls and presence default to contacts, direct
  messages to everyone. Blocks prevent future direct interactions, not shared-group visibility.
- Mail queue payloads are encrypted at rest with an operator-supplied key; this protects recovery
  secrets and does not introduce message E2EE. SMTP disabled means no fake send success.
- Do not implement messages, avatars, push, calls, deletion, or the M8 administration UI. Bootstrap
  operators, registration policy, and suspension are operator CLI capabilities with audit records.

## Review focus

1. Password verification racing with password change/suspension must not admit stale credentials;
   recheck user/session rows inside the admission transaction (Tasks 1-2).
2. A revoked or replaced session and its CSRF value must fail subsequent reads/mutations, including
   after a peer session changes the password (Tasks 1-2).
3. Concurrent email confirmations/reset consumers must preserve unique verified ownership and
   single-use challenges; enqueue and challenge creation must commit together (Task 4).
4. An expired/reclaimed mail lease cannot complete a newer claim, and a consumed/expired challenge
   must not be newly delivered; SMTP must run outside database locks (Task 4).
5. Late frontend responses and another tab's logout must not repopulate a previous user's private
   account state; demo storage must never become connected account state (Task 5).

## Task 4: Verified email, recovery, and durable mail delivery

**Files:** `src/accounts/email.rs`, `src/jobs/mod.rs`, `mail.rs`, `payload.rs`, mail migration,
SMTP/key configuration, Worker lifecycle integration, and `tests/recovery.rs`/`tests/jobs.rs`.

**Interfaces:** Email start/confirm/remove and generic recovery request/reset endpoints;
`MailQueue::claim` returns a job with a lease token; `deliver` checks current challenge eligibility
before SMTP; `complete/retry` require the matching unexpired fence. Mail payload binds job identity
as authenticated encryption context. Confirmation links put tokens in URL fragments, not queries.

- [ ] Add tests for disabled SMTP, atomic challenge/job creation, email replacement/uniqueness races,
      single-use reset, stale credential versions, encrypted payloads, expired challenge suppression,
      competing claims, crashed-worker reclaim, stale fences, retries, and queue capacity.
- [ ] Observe failures, then implement challenge transactions and AES-GCM payload protection. Keep
      old verified email until replacement succeeds; removal/password changes invalidate challenges.
- [ ] Implement bounded claims, 60-second leases, fenced completion, capped exponential retry and
      retained exhausted jobs. Initial mail budget is 10,000 unfinished jobs and five attempts.
      Worker shutdown stops new claims and bounds pending SMTP operations.
- [ ] Add optional Mailpit Compose profile and exercise actual SMTP delivery/capture and one-time
      links. Verify retry/reclaim with real PostgreSQL, then commit email/jobs separately as warranted.
